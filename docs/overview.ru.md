# Диспетчеры Codex

Этот каталог содержит пакет для делегированных запусков Codex CLI из Claude Code. Диспетчер
передаёт задачу раннеру, а наружу возвращает только путь к прогону и короткий статус. Полный
ответ, лог, снимки рабочего дерева и вычисленный по ним вердикт остаются в артефактах.

## Какой агент выбрать

| Агент | Доступ | Когда использовать |
| --- | --- | --- |
| `codex-scout` | `read-only` | Разобрать код, найти причину сбоя, собрать факты или ответить на несколько технических вопросов без правок. |
| `codex-build` | `workspace-write` | Реализовать изменение, исправить дефект, добавить тесты или документацию. Требует явного `--scope`. |
| `codex-review` | `read-only` | Получить независимое второе мнение по diff после реализации. Проверяет дефекты, а не стиль. |

### Жёсткая граница диспетчера

Диспетчер не выполняет заказ. Его единственная работа — запустить прогон через `run-codex.mjs` и
вернуть его результат. Если `run-codex.mjs` отсутствует, не запускается, завершается без строки
`RUN=`/`ATTACH=` или прогон не может начаться по любой другой причине, диспетчер обязан сразу
вернуть `FAIL — could not start the Codex run: <reason>` и остановиться.

Чтение кода, запись файлов и исправление тестов самим диспетчером в этой ситуации запрещены:
иначе Claude оплачивает именно ту работу, которую передача в Codex должна была вынести за пределы
своей квоты. Заявлять, что файлы созданы, без реально состоявшегося прогона нельзя ни при каких
условиях: нет прогона — нет результата. `SubagentStop` дополнительно блокирует ответ без папки
прогона, поэтому это правило проверяется и текстом, и внешним guard.

`codex-review` поддерживает области `uncommitted`, `base:<ветка>` и `commit:<sha>` через
`--mode`. По умолчанию он проверяет незакоммиченные изменения.

## Запуск

Задача поступает в `run-codex.mjs` через stdin. Примеры ниже предполагают установку пакета в
`~/.claude/agents/codex/`.

Разведка:

```bash
node ~/.claude/agents/codex/run-codex.mjs \
  --agent codex-scout \
  --repo . \
  --slug auth-flow \
  --effort medium < task.md
```

Имплементация:

```bash
node ~/.claude/agents/codex/run-codex.mjs \
  --agent codex-build \
  --repo . \
  --slug auth-flow \
  --scope "src/auth/**,tests/auth/**" \
  --verify "npm test" < task.md
```

Ревью незакоммиченных правок:

```bash
node ~/.claude/agents/codex/run-codex.mjs \
  --agent codex-review \
  --repo . \
  --slug auth-flow-review \
  --mode uncommitted < review-task.md
```

`--agent` обязателен. `--repo` по умолчанию равен текущему каталогу, `--slug` — суффиксу имени
агента, `--effort` — `medium`, `--mode` — `uncommitted`. Значение `--effort` передаётся Codex
как есть; раннер проверяет только, что это одно слово.

### Почему `--scope` обязателен

Для `codex-build` параметр `--scope` обязателен и содержит разделённые запятыми glob-шаблоны
относительно корня репозитория. Раннер отказывает до создания платного вызова, если scope пуст.

Формат шаблонов проверяется до старта Codex, у всех трёх агентов. Отказ приходит мгновенно и
бесплатно, если шаблон не может совпасть ни с чем: абсолютный или дисковый путь, обратные слэши,
сегмент `..`, либо шаблон, которому в репозитории не отвечает ни один файл. Список файлов берётся
у самого репозитория — `git ls-files --cached --others --exclude-standard`, то есть отслеживаемые
плюс новые незакоммиченные, без игнорируемого; каталог без git обходится вручную, минуя `.git` и
`node_modules`. До Plan_27 такой scope выяснялся только в вердикте — прогон 2026-08-09 с абсолютным
путём отработал 18 минут чужой квоты и получил `FAIL` за работу, которую сделал.

Файл, которого ещё нет, объявляется отдельно: `--scope-new "src/новый-модуль.mjs"`. Эти пути входят
в scope наравне с остальными и освобождены только от проверки существования; флаг принимает
`codex-build` — единственный агент, который создаёт файлы.

Scope нужен не только как инструкция в промпте. Перед запуском и после него раннер снимает
состояние дерева, вычисляет реально затронутые пути и завершает прогон с `FAIL`, если путь не
покрыт ни одним шаблоном. Служебные каталоги `.git/`, `.claude/`, `.codex/`, `.omx/`, `.omc/`
и `node_modules/` нельзя разрешить через scope. Пути, отнесённые конфигом к изменениям среды,
исключаются из этой проверки и отдельно записываются в отчёт.

### Почему `codex-build` объявляет исход

Ответ `codex-build` содержит обязательное поле `outcome`: `done` — заказанная работа выполнена,
`fail` — не выполнена по любой причине. Раннер не знает намерения заказа и потому не может
отличить «чинить было нечего» от «сделать не удалось»: прогон 2026-08-04 с задачей починить
функцию в отсутствующем модуле вернул `OK` при пустом дереве и зелёной проверке. Объявленный
`fail` даёт `FAIL` с причиной из `summary`; объявленный `done` ничего не доказывает — дерево,
scope и соответствие отчёта проверяются дальше как раньше. Подробности и порядок проверок — в
[verdict.md](verdict.md). У `codex-scout` и `codex-review` такого поля нет: их исход выражают
покрытие подвопросов и вердикт с находками.

### Повторный запуск и `--continue`

Цепочка — все прогоны с одним `slug` для одного и того же репозитория. Если такая цепочка уже
есть, новый запуск без `--continue` отклоняется до создания папки и расхода квоты. Это защищает
от случайного повтора.

Добавляйте `--continue` только для следующего захода по той же задаче, и только вместе с
разрешением в тексте задачи — флаг без разрешения отклоняется до расхода квоты:

```bash
node ~/.claude/agents/codex/run-codex.mjs \
  --agent codex-build \
  --repo . \
  --slug auth-flow \
  --continue \
  --scope "src/auth/**,tests/auth/**" < follow-up.md
```

где `follow-up.md` содержит строку с именем прогона и причиной:

```
continue: 2026-08-05_092913_auth-flow — LIMIT at step 3, tests unwritten
```

Разрешение одноразовое: оно называет последний прогон цепочки, а продолжение дописывает в неё более
поздний — та же строка второй раз не сработает. Подробности и все отказы — в
[run-lifecycle.md](run-lifecycle.md).

При сверке отчёта сборщика раннер учитывает накопленные изменения от состояния перед первым
прогоном цепочки до состояния после текущего. Поэтому продолжение может честно получить `OK`,
даже если нужные правки уже внесены предыдущим заходом. В `meta.json` это отмечается полем
`carried_from_earlier_run`.

## Почему обрыв вызова не теряет прогон

Раннер состоит из двух процессов:

- launcher проверяет аргументы и окружение, создаёт каталог и запускает worker;
- detached worker вызывает Codex, пишет снимки после запуска, считает вердикт и создаёт ответ.

Launcher печатает `RUN=<путь>` и ждёт `reply.txt`, но его обрыв не прерывает worker при обычном
завершении процесса или таймауте вызывающей оболочки. Worker не зависит от stdout диспетчера и
сам закрывает прогон артефактами. Убийство всего дерева процессов может завершить обе половины;
следующий запуск пометит оставшийся незакрытый прогон как `abandoned`.

## Артефакты

Корень задаёт переменная окружения `CODEX_RUNS_ROOT`. Пустое или отсутствующее значение означает
`~/.claude/codex-runs`. Каталог одного прогона имеет вид:

```text
<корень артефактов>/<папка проекта>/<дата_время>_<slug>/
```

Папка проекта названа по каталогу репозитория и помечена файлом `.project.json` с полным путём
этого репозитория. Маркер существует потому, что имя каталога проект не опознаёт: два разных
репозитория, оба названные `api`, писали бы в одну папку и смешивали историю — цепочки прогонов,
замок параллельного `codex-build` и учёт расхода читали бы чужие прогоны как свои. Занятое имя
уводит второй репозиторий в `api-2`, `api-3`.

Папки, созданные до появления маркера, усыновляются по полю `repo` из `status.json` их же
прогонов — ни один существующий архив не переезжает. Если в такой папке лежат прогоны двух
репозиториев, она достаётся тому, кто запускался там первым; второй получает имя с суффиксом.

Пути сравниваются нормализованными: прямые слэши, без хвостового слэша, на Windows без учёта
регистра. Симлинки и junction не разрешаются — `realpath` на Windows возвращает формы `\\?\` и
UNC, а это новый класс расхождений вместо решения старого.

Основные файлы:

| Файл | Назначение |
| --- | --- |
| `status.json` | Текущее состояние процесса и итоговый статус. Создаётся первым. |
| `task.md` | Дословная задача, вычисленные ограничения и инструкции выбранного агента. |
| `schema.json` | JSON Schema ответа Codex. |
| `worker.json` | Неизменяемый заказ, переданный launcher'ом worker'у. |
| `env.json` | Фактические настройки `hooks`, `plugins` и `environmentPaths` этого прогона. |
| `events.jsonl` | Поток событий Codex CLI под `--json`. По нему — и только по нему — определяется исчерпание квоты, расход и идентификатор сессии. Читается человеком через `codex-bridge read <прогон>`. |
| `stderr.log` | То, что CLI сказал вне протокола: паники, отказ на неизвестный флаг, отказы execpolicy. Пустым в норме не бывает — живая проба 2026-08-05 нашла там 488 байт у здорового прогона. |
| `result.json` | Структурированный ответ scout или build. |
| `review.json` | Структурированный ответ review. |
| `report.md` | Развёрнутый отчёт scout или build, извлечённый из JSON. |
| `meta.json` | Вердикт, причина, учёт токенов, окружение и изменения среды. |
| `reply.txt` | Короткий ответ диспетчеру; worker пишет его последним. |

Для scout могут появиться `questions.json`; для review и build — `scope.txt`; для build также
создаются снимки `head-*`, `git-*`, `state-*`, `diff.stat` и `flags.txt`.

### Посмотреть на хранилище прогонов

```bash
codex-bridge projects              # проекты: прогонов, вес, расход, живых сейчас, последний
codex-bridge projects codex-bridge # прогоны одного проекта: агент, вердикт, токены, вес
codex-bridge projects --json       # то же машине
codex-bridge read <прогон>         # ход одного прогона из его событий
```

Колонка «live now» считается тем же модулем, которым пользуются сторож ответа и замок дерева, —
единственный в пакете ответ на вопрос, идёт ли прогон прямо сейчас. Каталог с нечитаемыми
артефактами всё равно получает строку: инвентарь, скрывающий поломанное, бесполезен ровно тогда,
когда за ним и приходят. Прогон без учёта расхода не обнуляет сумму проекта — считаются известные.

### Чистка хранилища

```bash
codex-bridge prune <проект> <прогон>            # снять вес с одного прогона
codex-bridge prune <проект> <прогон> --purge    # снести папку прогона целиком
codex-bridge prune <проект>                     # снять вес со всех прогонов старше 30 дней
codex-bridge prune <проект> --purge             # снести папку проекта
codex-bridge prune --all-projects               # снять вес везде; с --purge запрещено
```

Щадящая чистка удаляет **только транспорт** — `events.jsonl`, `stderr.log` и архивный `raw.log`.
Учёт (`meta.json`), отчёт, результат и снимки дерева остаются: после неё цепочка заходов
по-прежнему считается, а работу прогона по-прежнему можно перечитать.

Три рубежа перед удалением, и ни один не обходится флагом:

- **без `-f` / `--force` не удаляется ничего** — команда печатает план и строку, которой его
  выполнить; план и исполнение приходят из одной функции, поэтому разойтись не могут;
- **подтверждение Yes/No на каждый удаляющий шаг** поверх флага: флаг говорит «я знаю, что делаю»,
  вопрос — «именно сейчас и именно это»;
- **нет терминала — нет удаления.** Агент запускает команды без TTY, и флага-обхода намеренно нет:
  он и был бы той самой лазейкой.

Возраст (`--older-than 30d`, `12h`, `2026-07-01`) читается **из имени папки**: скопированный или
восстановленный каталог врёт про свою дату в файловой системе, а имя — нет. Умолчание в 30 дней
принадлежит щадящей чистке; `--purge` никогда не стареет неявно — `prune sbx2 --purge` означает
эту папку, сейчас.

### Автоматическая чистка

Ключ `retention` в `run-config.json` (файл хоста, обновления его не трогают):

```json
"retention": { "enabled": true, "days": 30 }
```

Раннер перед созданием новой папки прогона снимает транспорт со своих прогонов старше указанного
срока. **Автоматика умеет ровно одно — снимать вес:** кода, который удалял бы `meta.json` или
каталог, в ней нет вовсе. Это не выключенная настройка, а отсутствующая возможность; включить её по
ошибке нельзя. Живые прогоны не трогаются никогда, а любой сбой чистки проглатывается — уборка,
способная сорвать запуск, хуже полного диска.

Удаление закрыто агентам двумя рубежами: команда отказывается работать без терминала, а хук
`prune-guard.mjs` (`PreToolUse`, `Bash|PowerShell`) отклоняет вызов ещё до того, как удаляющий
процесс будет создан. Ваш собственный терминал через хук не проходит — там `prune` работает как
обычно. `git prune` и `npm prune` сторож не трогает.

Сработав, она добавляет в короткий ответ диспетчера строку вида
`Retention: freed 41.2 MB from 12 runs older than 30 days`. Событие редкое, и молчание о нём стоило
бы дороже строки: человек, не понявший, куда делись файлы, идёт искать поломку. Про включённую
чистку предупреждают и `install`, и `doctor` — установщик, молча заводящий удаляющее поведение, это
сюрприз, а не удобство.

## Права команд оболочки

Необязательные правила для команд `codex-bridge` можно включить отдельно от установки:

```bash
node bin/codex-bridge.mjs permissions
node bin/codex-bridge.mjs permissions add
node bin/codex-bridge.mjs permissions remove
```

Без аргумента команда показывает состояние набора: `installed`, `partially installed` или
`absent`. `add` добавляет в `settings.json` выбранного хоста точные allow- и deny-строки для
обоих имён CLI, пути `node bin/codex-bridge.mjs`, Bash и PowerShell, не трогая чужие правила.
`remove` удаляет только эти строки из `allow`, `deny` и `ask`, поэтому похожая строка оператора
остаётся на месте. Доступны те же `--scope` и `--host`, что и у `install`; `uninstall` забирает
эти правила автоматически.

## Настройка среды

`run-config.json` управляет окружением делегированного Codex. По умолчанию `hooks` и `plugins`
выключены: раннер передаёт `--disable hooks --disable plugins`. Переключатели можно посмотреть
или изменить без ручного редактирования:

```bash
node ~/.claude/agents/codex/run-config.mjs
node ~/.claude/agents/codex/run-config.mjs plugins on
node ~/.claude/agents/codex/run-config.mjs hooks off
node ~/.claude/agents/codex/run-config.mjs reset
```

`models` задаёт, на чём идёт каждый режим: объект с ключами `scout`, `build`, `review`, в каждом
необязательные `model` и `effort`. Ключ редактируется прямо в файле — переключателем он не
является. Заданная модель уходит в `codex exec` флагом `-m`, а глубина рассуждения выбирается по
порядку: явный `--effort` запроса, затем профиль режима, затем `medium`. Пустой или отсутствующий
профиль означает «решает Codex»; идентификаторы моделей живут только здесь, в коде их нет.

```json
{
  "models": {
    "build": { "model": "gpt-5.6-luna", "effort": "max" }
  }
}
```

Файл `run-config.json` принадлежит хосту, а не пакету: установщик создаёт его один раз со
значениями по умолчанию и больше никогда не трогает — ни `install --force`, ни `update`, ни
`uninstall`. Настроенные профили переживают обновление пакета.

Запреты для делегированного прогона ставятся тем же установщиком: файл `codex-bridge.rules`
уезжает в `$CODEX_HOME/rules/` (по умолчанию `~/.codex/rules/`) и запрещает Codex команды,
меняющие историю, ветки и индекс репозитория. Личный `default.rules` оператора не изменяется:
Codex читает каталог целиком и применяет строжайшее из совпавших решений. Состояние файла
показывает `codex-bridge doctor`, обновляет `codex-bridge update`.

Субагентов делегированный прогон не заводит: раннер передаёт `-c agents.enabled=false`, поэтому
инструменты многоагентности исполнителю недоступны. Их правки иначе попали бы в снимок дерева как
работа самого прогона — мимо проверки scope, по которой его судят.

`budgets` — предел времени прогона в минутах по режимам: `scout` 15, `build` 25, `review` 20.
Ключ редактируется прямо в файле, значения — положительные числа; пустое поле считается ошибкой
конфига, а не отсутствием значения. По истечении предела worker убивает Codex вместе со всем
деревом процессов, записывает факт убийства полем `stopped_on_deadline` в `status.json` (вердикт
судит по полю, которое пишет раннер, а не по тексту, куда пишет и сам Codex) и закрывает каталог обычным вердиктом —
`FAIL` с причиной про дедлайн. Смысл предела в том, что «часами» становится невозможно по построению: ориентиром взят
самый долгий честный прогон проекта, шедший около двадцати минут.

```json
{
  "budgets": { "scout": 15, "build": 25, "review": 20 }
}
```

`answerLanguage` — язык, на котором прогон отвечает: `answer`, `report_markdown` и текстовые поля
`result.json`. Умолчание — `English`, независимо от языка задачи; ключ задаётся в `run-config.json`
непустой строкой, пустая строка отвергается при чтении. Без него язык выбирала модель — английский
заказ возвращался по-русски, и артефакты одного проекта выходили на двух языках.

`environmentPaths` — список glob-шаблонов для путей, которые во время прогона меняет окружающая
оснастка, а не сам Codex. Такие изменения не участвуют в проверке scope и соответствия отчёта
дереву, но остаются видимыми в `meta.json.environment_changes` и в коротком ответе. Список
редактируется непосредственно в `run-config.json`; это не переключатель. Некорректный JSON,
неизвестный ключ или значение неправильного типа останавливают запуск без расхода квоты.

Если ключ отсутствует, действуют пять шаблонов по умолчанию:

```json
[
  ".omc/**",
  ".claude/settings.local.json",
  "mcp-needs-auth-cache.json",
  "plugins/installed_plugins.json",
  "plugins/known_marketplaces.json"
]
```

Пустой список явно означает, что ни один путь не считается изменением среды.

## Свод конвенций

Правила проекта доходили до прогона только тогда, когда оркестратор не забыл написать в задаче
«прочитай CLAUDE.md». Забыл — прогон работал без правил, и приёмка ловила один и тот же класс
нарушений шесть заходов подряд. Теперь свод вклеивается в `task.md` каждого прогона отдельной
секцией `## Conventions`, в двух слоях:

- `~/.claude/agents/codex/conventions.md` — общий свод хоста. Файл **seeded**: установщик кладёт
  его один раз и больше не трогает, как `run-config.json`. Правится оператором без релиза пакета.
- `.codex-conventions.md` в корне самого репозитория — необязательный слой особенностей проекта.
  Едет вместе с проектом; нет файла — слой молча пропускается.

Нет обоих — секции в задаче нет вовсе, и это не ошибка. Пустой (или из одних пробелов) файл слоя
тоже не даёт секции: пустой свод в артефакте читался бы как «правила выдали и проигнорировали».
Про пустой файл предупреждает `doctor` строкой `conventions: … (found but empty)`.

Текст именно **вклеивается**, а не упоминается ссылкой: «прочитай файл X» — надежда, прогон волен
не прочитать. Это то же решение, что перечень обязательных входов Plan_13. Побочный эффект полезен
сам по себе: через месяц по `task.md` видно, по каким правилам прогон судили.

Весь `CLAUDE.md` не вклеивается намеренно — больше половины его про Telegram, бэкапы, релизы и UI,
к прогону Codex отношения не имеющие: лишний текст в каждой задаче не бесплатен и размывает то,
что действительно надо соблюсти.

## Сторож ответа

`hooks/reply-guard.mjs` — хук `SubagentStop` для трёх диспетчеров. Он проверяет, что ответ:

- содержит `RUN=` с существующим каталогом;
- не выдан поверх живого или брошенного прогона без вердикта;
- **называет каждый живой прогон `codex-build` этого проекта, а не только тот, что процитирован**;
- подтверждён `meta.json`;
- не объявляет статус, противоречащий `meta.json.status`.

Третья проверка появилась после 2026-08-05: диспетчер вернул вердикт первого прогона, оставив
второй работать в фоне, и оркестратор правил файлы в дереве, которое чужой прогон снимал до и
после себя. Сторож читает всю папку прогонов проекта, поэтому умолчание больше не работает: факт
берётся с диска, а не из текста ответа. Считаются только прогоны `codex-build` — разведка и ревью
живут в песочнице `read-only`, дерева не касаются, и запускать их рядом с другой работой
нормально; блокировать ответ из-за читающего прогона значило бы тратить бюджет попыток, а затем и
ход, на прогон, который ничему не мешает.

Сторож может остановить ход, потому что обещание «прогон ещё идёт» не является результатом, а
работающее дерево в это время занято worker'ом. Ошибки формы блокируются ограниченное число раз;
для внешнего состояния после исчерпания попыток сторож завершает ход через `continue: false`,
чтобы неподтверждённый ответ не прошёл молча.

## Замок дерева

`hooks/worktree-lock.mjs` — хук `PreToolUse` на инструменты записи файлов (`Write`, `Edit`,
`MultiEdit`, `NotebookEdit`). Он отклоняет правку, если файл лежит внутри репозитория, который
держит живой прогон `codex-build`, и называет каталог прогона, агента, slug и репозиторий.

Сторож сообщает, замок не пускает: узнать о чужом прогоне и не мочь испортить его снимок — разные
вещи, а инцидент 2026-08-05 стоил ложных падений тестов именно на второй. Пути сравниваются как
везде в пакете — прямые слэши, без хвостового, без учёта регистра и без `realpath`.

Известное ограничение: правка через `Bash` (например `sed -i`) замок обходит. Разбирать командную
строку ненадёжно, а блокировать `Bash` целиком нельзя — прогону нужны сборка и тесты.

## Установка в другую конфигурацию Claude Code

1. Скопируйте весь каталог `agents/codex/` в `~/.claude/agents/codex/`. В него входят три
   определения агентов, раннер, модули вердикта, guard и конфиг.
2. Зарегистрируйте `agents/codex/hooks/reply-guard.mjs` в `settings.json` как command-hook группы
   `hooks.SubagentStop`. Matcher может охватывать всех субагентов: guard сам пропускает типы,
   отличные от `codex-scout`, `codex-build` и `codex-review`.
3. Скопируйте каталог `commands/codex/` в `~/.claude/commands/codex/`, если нужны команды
   `/codex:env` и `/codex:usage`.
4. Проверьте `codex --version` и авторизацию Codex CLI.

Минимальный фрагмент регистрации guard:

```json
{
  "hooks": {
    "SubagentStop": [
      {
        "matcher": "*",
        "hooks": [
          {
            "type": "command",
            "command": "node \"$HOME/.claude/agents/codex/hooks/reply-guard.mjs\"",
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

Если в `settings.json` уже есть `SubagentStop`, добавьте command-hook в существующую структуру,
не заменяя другие hooks.

Файлы `commands/codex/` должны ехать именно копией. Claude Code определяет namespace команды по
физическому расположению файла и не понимает симлинки или файлы-указатели для этой задачи.
