# Диспетчеры Codex

Этот каталог содержит пакет для делегированных запусков Codex CLI из Claude Code. Диспетчер
передаёт задачу раннеру, а наружу возвращает только путь к прогону и короткий статус. Полный
ответ, лог, снимки рабочего дерева и вычисленный по ним вердикт остаются в артефактах.

## Какой агент выбрать

| Агент | Доступ | Когда использовать |
| --- | --- | --- |
| `codex-scout` | `read-only` | Разобрать код, найти причину сбоя, собрать факты или ответить на несколько технических вопросов без правок. |
| `codex-build` | `workspace-write` | Реализовать изменение, исправить дефект, добавить тесты или документацию. Требует явного `--scope`. |
| `codex-review` | `read-only` | Получить независимое второе мнение по diff после реализации. Проверяет дефекты, а не стиль. |

`codex-review` поддерживает области `uncommitted`, `base:<ветка>` и `commit:<sha>` через
`--mode`. По умолчанию он проверяет незакоммиченные изменения.

## Запуск

Задача поступает в `run-codex.mjs` через stdin. Примеры ниже предполагают установку пакета в
`~/.claude/agents/codex/`.

Разведка:

```bash
node ~/.claude/agents/codex/run-codex.mjs \
  --agent codex-scout \
  --repo . \
  --slug auth-flow \
  --effort medium < task.md
```

Имплементация:

```bash
node ~/.claude/agents/codex/run-codex.mjs \
  --agent codex-build \
  --repo . \
  --slug auth-flow \
  --scope "src/auth/**,tests/auth/**" \
  --verify "npm test" < task.md
```

Ревью незакоммиченных правок:

```bash
node ~/.claude/agents/codex/run-codex.mjs \
  --agent codex-review \
  --repo . \
  --slug auth-flow-review \
  --mode uncommitted < review-task.md
```

`--agent` обязателен. `--repo` по умолчанию равен текущему каталогу, `--slug` — суффиксу имени
агента, `--effort` — `medium`, `--mode` — `uncommitted`. Значение `--effort` передаётся Codex
как есть; раннер проверяет только, что это одно слово.

### Почему `--scope` обязателен

Для `codex-build` параметр `--scope` обязателен и содержит разделённые запятыми glob-шаблоны
относительно корня репозитория. Раннер отказывает до создания платного вызова, если scope пуст.

Scope нужен не только как инструкция в промпте. Перед запуском и после него раннер снимает
состояние дерева, вычисляет реально затронутые пути и завершает прогон с `FAIL`, если путь не
покрыт ни одним шаблоном. Служебные каталоги `.git/`, `.claude/`, `.codex/`, `.omx/`, `.omc/`
и `node_modules/` нельзя разрешить через scope. Пути, отнесённые конфигом к изменениям среды,
исключаются из этой проверки и отдельно записываются в отчёт.

### Повторный запуск и `--continue`

Цепочка — все прогоны с одним `slug` для одного и того же репозитория. Если такая цепочка уже
есть, новый запуск без `--continue` отклоняется до создания папки и расхода квоты. Это защищает
от случайного повтора.

Добавляйте `--continue` только для следующего захода по той же задаче:

```bash
node ~/.claude/agents/codex/run-codex.mjs \
  --agent codex-build \
  --repo . \
  --slug auth-flow \
  --continue \
  --scope "src/auth/**,tests/auth/**" < follow-up.md
```

При сверке отчёта сборщика раннер учитывает накопленные изменения от состояния перед первым
прогоном цепочки до состояния после текущего. Поэтому продолжение может честно получить `OK`,
даже если нужные правки уже внесены предыдущим заходом. В `meta.json` это отмечается полем
`carried_from_earlier_run`.

## Почему обрыв вызова не теряет прогон

Раннер состоит из двух процессов:

- launcher проверяет аргументы и окружение, создаёт каталог и запускает worker;
- detached worker вызывает Codex, пишет снимки после запуска, считает вердикт и создаёт ответ.

Launcher печатает `RUN=<путь>` и ждёт `reply.txt`, но его обрыв не прерывает worker при обычном
завершении процесса или таймауте вызывающей оболочки. Worker не зависит от stdout диспетчера и
сам закрывает прогон артефактами. Убийство всего дерева процессов может завершить обе половины;
следующий запуск пометит оставшийся незакрытый прогон как `abandoned`.

## Артефакты

Корень задаёт переменная окружения `CODEX_RUNS_ROOT`. Пустое или отсутствующее значение означает
`~/.claude/codex-runs`. Каталог одного прогона имеет вид:

```text
<корень артефактов>/<папка проекта>/<дата_время>_<slug>/
```

Папка проекта названа по каталогу репозитория и помечена файлом `.project.json` с полным путём
этого репозитория. Маркер существует потому, что имя каталога проект не опознаёт: два разных
репозитория, оба названные `api`, писали бы в одну папку и смешивали историю — цепочки прогонов,
замок параллельного `codex-build` и учёт расхода читали бы чужие прогоны как свои. Занятое имя
уводит второй репозиторий в `api-2`, `api-3`.

Папки, созданные до появления маркера, усыновляются по полю `repo` из `status.json` их же
прогонов — ни один существующий архив не переезжает. Если в такой папке лежат прогоны двух
репозиториев, она достаётся тому, кто запускался там первым; второй получает имя с суффиксом.

Пути сравниваются нормализованными: прямые слэши, без хвостового слэша, на Windows без учёта
регистра. Симлинки и junction не разрешаются — `realpath` на Windows возвращает формы `\\?\` и
UNC, а это новый класс расхождений вместо решения старого.

Основные файлы:

| Файл | Назначение |
| --- | --- |
| `status.json` | Текущее состояние процесса и итоговый статус. Создаётся первым. |
| `task.md` | Дословная задача, вычисленные ограничения и инструкции выбранного агента. |
| `schema.json` | JSON Schema ответа Codex. |
| `worker.json` | Неизменяемый заказ, переданный launcher'ом worker'у. |
| `env.json` | Фактические настройки `hooks`, `plugins` и `environmentPaths` этого прогона. |
| `raw.log` | Поток stdout/stderr Codex. |
| `result.json` | Структурированный ответ scout или build. |
| `review.json` | Структурированный ответ review. |
| `report.md` | Развёрнутый отчёт scout или build, извлечённый из JSON. |
| `meta.json` | Вердикт, причина, учёт токенов, окружение и изменения среды. |
| `reply.txt` | Короткий ответ диспетчеру; worker пишет его последним. |

Для scout могут появиться `questions.json`; для review и build — `scope.txt`; для build также
создаются снимки `head-*`, `git-*`, `state-*`, `diff.stat` и `flags.txt`.

## Настройка среды

`run-config.json` управляет окружением делегированного Codex. По умолчанию `hooks` и `plugins`
выключены: раннер передаёт `--disable hooks --disable plugins`. Переключатели можно посмотреть
или изменить без ручного редактирования:

```bash
node ~/.claude/agents/codex/run-config.mjs
node ~/.claude/agents/codex/run-config.mjs plugins on
node ~/.claude/agents/codex/run-config.mjs hooks off
node ~/.claude/agents/codex/run-config.mjs reset
```

`models` задаёт, на чём идёт каждый режим: объект с ключами `scout`, `build`, `review`, в каждом
необязательные `model` и `effort`. Ключ редактируется прямо в файле — переключателем он не
является. Заданная модель уходит в `codex exec` флагом `-m`, а глубина рассуждения выбирается по
порядку: явный `--effort` запроса, затем профиль режима, затем `medium`. Пустой или отсутствующий
профиль означает «решает Codex»; идентификаторы моделей живут только здесь, в коде их нет.

```json
{
  "models": {
    "build": { "model": "gpt-5.6-luna", "effort": "max" }
  }
}
```

Файл `run-config.json` принадлежит хосту, а не пакету: установщик создаёт его один раз со
значениями по умолчанию и больше никогда не трогает — ни `install --force`, ни `update`, ни
`uninstall`. Настроенные профили переживают обновление пакета.

Запреты для делегированного прогона ставятся тем же установщиком: файл `codex-bridge.rules`
уезжает в `$CODEX_HOME/rules/` (по умолчанию `~/.codex/rules/`) и запрещает Codex команды,
меняющие историю, ветки и индекс репозитория. Личный `default.rules` оператора не изменяется:
Codex читает каталог целиком и применяет строжайшее из совпавших решений. Состояние файла
показывает `codex-bridge doctor`, обновляет `codex-bridge update`.

Субагентов делегированный прогон не заводит: раннер передаёт `-c agents.enabled=false`, поэтому
инструменты многоагентности исполнителю недоступны. Их правки иначе попали бы в снимок дерева как
работа самого прогона — мимо проверки scope, по которой его судят.

`budgets` — предел времени прогона в минутах по режимам: `scout` 15, `build` 25, `review` 20.
Ключ редактируется прямо в файле, значения — положительные числа; пустое поле считается ошибкой
конфига, а не отсутствием значения. По истечении предела worker убивает Codex вместе со всем
деревом процессов, дописывает в `raw.log` строку о причине остановки и закрывает каталог обычным
вердиктом. Смысл предела в том, что «часами» становится невозможно по построению: ориентиром взят
самый долгий честный прогон проекта, шедший около двадцати минут.

```json
{
  "budgets": { "scout": 15, "build": 25, "review": 20 }
}
```

`answerLanguage` — язык, на котором прогон отвечает: `answer`, `report_markdown` и текстовые поля
`result.json`. Умолчание — `English`, независимо от языка задачи; ключ задаётся в `run-config.json`
непустой строкой, пустая строка отвергается при чтении. Без него язык выбирала модель — английский
заказ возвращался по-русски, и артефакты одного проекта выходили на двух языках.

`environmentPaths` — список glob-шаблонов для путей, которые во время прогона меняет окружающая
оснастка, а не сам Codex. Такие изменения не участвуют в проверке scope и соответствия отчёта
дереву, но остаются видимыми в `meta.json.environment_changes` и в коротком ответе. Список
редактируется непосредственно в `run-config.json`; это не переключатель. Некорректный JSON,
неизвестный ключ или значение неправильного типа останавливают запуск без расхода квоты.

Если ключ отсутствует, действуют пять шаблонов по умолчанию:

```json
[
  ".omc/**",
  ".claude/settings.local.json",
  "mcp-needs-auth-cache.json",
  "plugins/installed_plugins.json",
  "plugins/known_marketplaces.json"
]
```

Пустой список явно означает, что ни один путь не считается изменением среды.

## Сторож ответа

`hooks/reply-guard.mjs` — хук `SubagentStop` для трёх диспетчеров. Он проверяет, что ответ:

- содержит `RUN=` с существующим каталогом;
- не выдан поверх живого или брошенного прогона без вердикта;
- подтверждён `meta.json`;
- не объявляет статус, противоречащий `meta.json.status`.

Сторож может остановить ход, потому что обещание «прогон ещё идёт» не является результатом, а
работающее дерево в это время занято worker'ом. Ошибки формы блокируются ограниченное число раз;
для внешнего состояния после исчерпания попыток сторож завершает ход через `continue: false`,
чтобы неподтверждённый ответ не прошёл молча.

## Установка в другую конфигурацию Claude Code

1. Скопируйте весь каталог `agents/codex/` в `~/.claude/agents/codex/`. В него входят три
   определения агентов, раннер, модули вердикта, guard и конфиг.
2. Зарегистрируйте `agents/codex/hooks/reply-guard.mjs` в `settings.json` как command-hook группы
   `hooks.SubagentStop`. Matcher может охватывать всех субагентов: guard сам пропускает типы,
   отличные от `codex-scout`, `codex-build` и `codex-review`.
3. Скопируйте каталог `commands/codex/` в `~/.claude/commands/codex/`, если нужны команды
   `/codex:env` и `/codex:usage`.
4. Проверьте `codex --version` и авторизацию Codex CLI.

Минимальный фрагмент регистрации guard:

```json
{
  "hooks": {
    "SubagentStop": [
      {
        "matcher": "*",
        "hooks": [
          {
            "type": "command",
            "command": "node \"$HOME/.claude/agents/codex/hooks/reply-guard.mjs\"",
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

Если в `settings.json` уже есть `SubagentStop`, добавьте command-hook в существующую структуру,
не заменяя другие hooks.

Файлы `commands/codex/` должны ехать именно копией. Claude Code определяет namespace команды по
физическому расположению файла и не понимает симлинки или файлы-указатели для этой задачи.
